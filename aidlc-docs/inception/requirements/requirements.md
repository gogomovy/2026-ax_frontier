# Requirements: AX프런티어 AI Agent — 종합기획부 Persona

## Intent Analysis

| Attribute | Value |
|---|---|
| **User Request** | 종합기획부 Persona Journey에 해당하는 제품을 AI-DLC Inception으로 정의하고 이후 구현한다 |
| **Request Type** | New Project (greenfield) |
| **Scope Estimate** | Multiple components — Dashboard, 경영목표, Knowledge DB, Agent, 전파용 데이터 모델 |
| **Complexity Estimate** | Complex — 다출처 근거, LLM, 문서 파싱, 공식 도메인 검색, 역할별 확장 구조 |

### 제품이 하는 일

은행 경영목표·KPI와 사업 데이터를 연결해, 종합기획부가 **어디에 Attention을 둘지, 경영목표를 어떻게 수정·신설할지**를 판단하도록 지원한다. 확정된 목표는 이후 사업부서·영업점 Agent의 공통 판단 기준으로 저장된다.

단순 Dashboard, 질문 대기형 챗봇, 근거 없는 목표 숫자 생성이 아니다.

### 핵심 루프

MONITOR → INTERPRET → SET DIRECTION → PROPAGATE

## 1. 범위

### IN

- 종합기획부 Persona의 Journey A~D
- 기획안 MUST 전부
- 기획안 SHOULD 전부 (Q14 BCDEFG + Q13/C4의 외부 검색·기사 확정)
- 이후 신용리스크관리부·영업점 화면이 붙을 수 있는 계정·권한·라우팅·데이터 모델 구조

### OUT (이번 Prototype)

- 신용리스크관리부·영업점의 실제 업무 화면 (로그인 시 ‘이후 구현’ 안내만)
- 사업부서용 수신 화면으로 전파를 시연하는 것 (저장·스키마만)
- 실제 사내 인증·결재 워크플로
- 은행 전 사업부문 상세 Dashboard
- 전사 시스템 실시간 연계, 전 문서 자동수집
- 정교한 목표값 추천 알고리즘 (LLM이 단일 확정 숫자를 만들지 않음)
- Security extension (opt-out)
- 클라우드 배포

## 2. Functional Requirements

### FR-1 진입과 Persona

- **FR-1.1** Mock 로그인: 아이디(또는 동등한 선택)로 Persona 권한을 고른다.
- **FR-1.2** 계정은 세 Persona(종합기획부, 신용리스크관리부, 영업점)가 모두 목록에 있고 로그인된다.
- **FR-1.3** 종합기획부 계정은 은행 전체 Dashboard로 진입한다.
- **FR-1.4** 나머지 계정은 실제 업무 화면 없이 ‘이후 구현’ 안내만 본다.
- **FR-1.5** 권한·Persona 식별은 이후 화면 연결이 가능하도록 데이터와 라우팅에 남긴다. 실제 SSO/사내 인증은 구현하지 않는다.

### FR-2 공통 UX와 Agent 원칙

- **FR-2.1** Dashboard First. 빈 채팅창에서 시작하지 않는다. 화면 진입 시 Agent가 이미 Attention·보고를 보여 준다.
- **FR-2.2** 사용자는 Dashboard 또는 Agent 결과를 기준으로 자연어 추가 질문을 할 수 있다 (SHOULD).
- **FR-2.3** Evidence First. 경영목표 수정·신규 제안에 근거가 없으면 출력하지 않는다. 근거 없는 “목표를 N%로 바꾸라” 금지를 지킨다.
- **FR-2.4** Traceability: 판단 → 근거 → 데이터 또는 문서 → 원문 확인.
- **FR-2.5** Unsupported Causality 금지. 상관·기여를 원인으로 단정하지 않는다. “주요 기여 영역”, “원인 후보” 등으로 쓴다.
- **FR-2.6** UI와 Agent는 한/영 전환 가능, **기본 언어는 한국어**.
- **FR-2.7** 코드·식별자·저장소 파일명은 영어를 기본으로 한다 (구현 관례). 사용자에게 보이는 문자열은 기본 한국어.

### FR-3 상위 Navigation

- **FR-3.1** 상위 영역 세 개: 은행 Dashboard, 경영목표 설정, 데이터베이스.
- **FR-3.2** Tab 또는 동등한 Navigation으로 이동한다. 세부 레이아웃은 Construction에서 정한다.

### FR-4 은행 Dashboard (Journey A)

- **FR-4.1** 상단에 사업부문 카드: 여신, 수신, 퇴직연금, 자산관리, 신탁, 외환, 카드. 세계관을 보여 준다.
- **FR-4.2** 여신 카드만 상세 Dashboard로 들어간다. 나머지 카드는 상세 화면이 없다.
- **FR-4.3** AI 주요 Attention과 확인·보고 요청을 UI에서 구분한다.

#### Attention

- **FR-4.4** 여신 Attention은 LLM이 실적·목표·정책 요약을 읽고 고른다. 각 Attention에 근거 데이터 ID를 붙인다.
- **FR-4.5** 메인 Dashboard에는 사업부문별 Attention 1~2개를 **notification list 형태의 요약 목록**으로 보여 준다. 카드 클릭 전에는 이 목록으로 전체를 본다.
- **FR-4.6** 사업부문 카드를 누르면 그 부문의 Attention이 보인다.
- **FR-4.7** 여신이 아닌 카드의 Attention은 **고정 Mock 문구**이다. LLM은 여신에만 돌린다.
- **FR-4.8** 상위 화면에서 본 Attention이 있으면, 해당 사업 상세 화면에서도 그 Attention과 근거를 다시 보여 준다.

#### 확인·보고 요청

- **FR-4.9** 타 조직에서 올라온 확인·보고 요청을 Attention과 **별도 영역**에 표시한다.
- **FR-4.9.1** 요청은 화면 전용 Mock이 아니라 **공유 저장소(PostgreSQL)의 동일 레코드**다. 종합기획부 Dashboard는 이 저장소를 읽어 보여 준다.
- **FR-4.9.2** 이번 Prototype에서는 시드(미리 생성한 값)로 목록을 채운다. 시드 예시는 기획안 DASH-04를 따른다 (사업부서 성과 확인 요청, 전기 사업 성과보고, 경영방향 확인, 영업점·지역본부 보고 등).
- **FR-4.9.3** 이후 사업부서·영업점 Journey가 확인·보고 요청을 **생성**하면, 같은 저장소에 쌓이고 종합기획부 화면에는 **추가 연동 화면 없이 같은 목록으로** 보여야 한다. 생성 API·스키마(요청 주체 Persona, 조직, 사업부문, 제목, 본문, 상태, 생성 시각 등)를 이번 범위에서 둔다.
- **FR-4.9.4** 이번 범위에서 사업부서·영업점의 ‘요청 올리기’ UI는 만들지 않는다. 시드와 API만으로 연결을 증명할 수 있게 한다.

#### 경영목표 검토 연결 (SHOULD / DASH-05)

- **FR-4.10** Attention 또는 보고 이슈를 ‘경영목표 검토에 반영’으로 저장할 수 있다.
- **FR-4.11** 경영목표 설정 화면에 진입하면 ‘최근 경영목표 검토 필요사항’으로 이 목록을 보여 준다.

### FR-5 여신 상세

- **FR-5.1** 여신 상세의 핵심 영역은 여신 종합수익, 기업여신, 가계여신 세 가지다.
- **FR-5.2** 중간 깊이 UI. 지표 목록은 교체 가능하게 둔다. 실제 당행 화면 복제는 자료 도착 후다.
- **FR-5.3** 공통 비교 기준: 현재값, 전년 동분기 실적, 증감액, 증감률, Agent 요약.
- **FR-5.4** Agent는 해당 화면 실적을 해설한다. 표현은 추후 당행 보고문서를 참고해 조정한다. 자료 전에는 위 비교 구조로 해설한다.

#### 여신 종합수익

- **FR-5.5** 여신 분야 **종합수익 단일 값**만 둔다.
- **FR-5.6** FR-5.3 비교와 Agent 요약을 제공한다.

#### 기업여신

- **FR-5.7** 지표:
  - 기업여신 잔액
  - 전년 동분기 대비 증가율
  - 신규 취급액
  - 현재 경영목표 대비 Gap
  - 연체율
  - 부실률
  - 예상손실
  - 신용등급별 분포
  - 등급별 부도율
- **FR-5.8** 현재 설정된 기업여신 관련 경영목표를 함께 보여 줄 수 있다.

#### 가계여신

- **FR-5.9** 지표:
  - 가계여신 잔액
  - 전년 동분기 대비 증가율
  - 관리목표 대비 현재 수준
  - 연체율
  - 부실률
  - 신용등급 분포 (금액 기준, 건수 기준)
  - 등급별 부도율
- **FR-5.10** 포용금융 관련 지표(중·저신용자 비중, 관련 공급액 등)를 **가계여신 상세에 표시**하고, 신규 경영목표 제안 근거로도 사용한다.

### FR-6 경영목표 설정 (Journey B)

- **FR-6.1** Dashboard 상단 Navigation으로 경영목표 설정에 들어간다.
- **FR-6.2** 초기 화면은 사업부문 카드. **여신**만 실제 설정 화면으로 동작한다.
- **FR-6.3** 여신 설정 화면은 개념적으로 좌측 현재 경영목표 List, 우측 Agent 검토·제안이다. 구체 Layout은 Construction에서 정한다.

#### 목표 목록과 상태

- **FR-6.4** 현재 적용 중인 여신 경영목표를 List로 보여 준다. 초기 Mock 예시는 기획안 GOAL-04를 따른다. 실제 당행 사업계획 도착 시 교체한다.
- **FR-6.5** 상태 구분: 현재 적용 중, AI 수정 제안, 수정 검토 중. 복잡한 결재는 없다. 사용자가 **확인**한 목표가 시스템상 현재 목표다.
- **FR-6.6** 경영목표 변경 History를 남긴다 (SHOULD).

#### 기존 목표 수정

- **FR-6.7** Agent는 각 목표를 검토해 필요 시 수정안을 제안한다. Demo 중점: 기업여신 확대, 가계여신 관리·축소.
- **FR-6.8** 수정 제안은 세 근거를 고려한다: (1) 당행 현황 Data (2) 정부정책·외부 환경 (3) 경영 의사결정사항 DB.
- **FR-6.9** “왜 수정해야 하는가”와 “왜 이 숫자인가”를 분리한다.
- **FR-6.10** 수치 추천은 **방향 + 범위**이다. 단일 확정 숫자는 사용자가 고른다. LLM이 임의로 확정 목표값을 만들지 않는다.
- **FR-6.11** 사용자 Action: 기존 목표 유지, Agent 제안 반영, 직접 수정. **Agent 제안 반영**은 (1) 제안을 그대로 확인하는 것과 (2) 제안 내용을 일부 수정한 뒤 확인하는 것을 모두 포함한다. 어느 쪽이든 확인 시 현재 목표에 반영한다. 생성방식은 그대로 반영이면 AI 제안 기반, 일부 수정 후 반영이면 AI 제안 기반으로 두되 사용자 수정이 History에 남는다.

#### 신규 목표

- **FR-6.12** Agent는 기존에 없는 신규 목표를 제안할 수 있다. Prototype 핵심 예: **포용금융 공급 확대**.
- **FR-6.13** 신규 제안에도 FR-6.8과 같은 세 근거를 쓴다. **포용금융 공급 확대** 데모 제안의 근거는 다음을 **모두** 포함한다.
  - 당행 현황: 가계여신 상세의 중·저신용자 비중·공급액 등 (FR-5.10)
  - 외부: 정부 및 외부 금융기관의 포용금융 확대 요청·기조를 다루는 **언론보도 자료** (데모용 시드. 근거로 쓰려면 FR-7.10에 따라 확정된 기사여야 하며, 데모 시드는 확정 상태로 넣는다)
  - 내부: 행 내 경영 의사결정사항 중 **포용금융 확대 관련 논의** (데모용 시드 문서)
- **FR-6.14** 신규 제안 UI 최소 정보: 목표명, 제안 이유, 근거 ① 당행 현황, 근거 ② 정부정책·외부 보도, 근거 ③ 경영 의사결정, ‘경영목표로 추가’.
- **FR-6.15** 사용자는 신규 목표를 (1) Agent 제안 그대로 추가하거나, (2) Agent 제안을 일부 수정한 뒤 추가하거나, (3) 별도 입력으로 직접 등록할 수 있다. (1)(2)는 생성방식 AI 제안 기반이며, (2)는 History에 사용자 수정이 남는다. (3)은 사용자 직접 입력이다.

#### 확정·저장

- **FR-6.16** 확인 후 현재 경영목표로 저장한다. 최소 필드: 사업부문, 내용, 목표값 또는 관리방향, 적용기간, 생성·수정일, 생성방식(기존 / 사용자 직접 / AI 제안 기반), 상태.
- **FR-6.17** 확정된 목표는 해당 사업부문의 현재 경영목표로 남고, 이후 사업부서 Journey가 읽을 수 있는 구조여야 한다. 이번 Prototype은 **저장과 스키마**까지이며 사업부서 화면은 만들지 않는다.

### FR-7 데이터베이스 (Journey C)

- **FR-7.1** 초기 화면 Card 두 개: 정부정책 데이터베이스, 경영 의사결정사항 데이터베이스.
- **FR-7.2** 정부정책 DB: Agent가 목표 판단에 쓰는 외부 정책 문서. 업로드 지원: PDF, 텍스트, HWP.
- **FR-7.3** HWP: 텍스트를 추출하고 Agent가 그 텍스트를 근거로 읽는다. 화면에서 원본 다운로드와 추출 텍스트/요약을 확인한다. 브라우저 HWP 뷰어는 범위 밖이다.
- **FR-7.4** 정부정책 문서 Metadata 최소: 문서명, 기관, 정책 또는 기준일, 등록일, 적용 사업부문, Tag.
- **FR-7.5** 경영 의사결정사항 DB: 경영전략회의, 사업계획, 경영진 방향, 내부 보고, 회의 결과 등. Metadata 최소: 문서명, 회의 또는 출처, 의사결정일, 등록일, 적용 사업부문, Tag.
- **FR-7.6** Agent는 현재 사업부문·목표와 **관련된 문서만** 선택적으로 사용한다. 전 문서 무조건 투입 금지.
- **FR-7.7** 근거 원문 확인: 문서명, 출처, 날짜, Agent가 참고한 내용 또는 요약, 원본 파일 열기.

#### 외부 검색과 기사 확정

- **FR-7.8** 실시간 검색은 **지정 공식 도메인만** 한다. 기본 대상: 금융위원회, 금융감독원, 기획재정부. 목록은 설정으로 관리할 수 있게 둔다.
- **FR-7.9** 공식 도메인 검색 결과는 Agent 근거로 쓸 수 있다. 근거 표시에서 당행 Data / 내부 경영방향 / 외부 정책(공식)을 구분한다.
- **FR-7.10** 정책 관련 **기사**는 실시간 검색 근거로 자동 사용하지 않는다. 정부정책/기사 DB 관리 화면에 Agent가 모아 둔 기사 후보가 보이고, 사용자가 **근거로 쓸지 확정**한 기사만 근거가 된다.
- **FR-7.11** 사용자가 직접 넣은 기사 문서도, 확정된 것만 근거로 쓴다.

### FR-8 전파 (Journey D)

- **FR-8.1** 종합기획부가 확정한 경영목표는 해당 사업부문의 현재 목표로 PostgreSQL에 저장된다.
- **FR-8.2** 이후 사업부서 화면이 (1) 현재 목표로 표시 (2) Agent 판단 기준 (3) Action 제안 근거로 쓸 수 있도록 모델과 API를 둔다.
- **FR-8.3** 이번 범위에서 사업부서 화면·미리보기는 만들지 않는다.
- **FR-8.4** 반대 방향: 사업부서·영업점이 올린 확인·보고 요청은 FR-4.9의 공유 저장소로 들어온다. 목표 전파와 요청 수신은 같은 ‘이후 Journey 연결’ 구조다.

### FR-9 데모 데이터와 관리

- **FR-9.1** 기획 예시 시나리오를 재현하는 Mock을 넣는다: 기업여신 목표 하회, 가계여신 관리목표 상단 근접, 포용금융 신규 목표. 포용금융 데모에는 가계여신 중·저신용 지표뿐 아니라, 정부·외부 금융기관 포용금융 확대 관련 **확정 상태 언론보도 시드**와 행 내 **포용금융 확대 논의 경영의사결정 시드**를 포함한다.
- **FR-9.2** 관리 화면에서 숫자·목표를 바꿔 다른 시나리오를 보여 줄 수 있다.
- **FR-9.3** 당행 실제 자료 도착 전 이 Mock/Sample Logic을 사용한다.

### FR-10 코드 위치

- **FR-10.1** 애플리케이션 코드는 워크스페이스 루트의 모노레포 `apps/web`, `apps/api`에 둔다.
- **FR-10.2** `aidlc-docs/`와 `aidlc-workflows/`에는 제품 코드를 두지 않는다.

## 3. Non-Functional Requirements

### NFR-1 실행 환경

- **NFR-1.1** 로컬 개발 서버만. 클라우드 배포는 하지 않는다.
- **NFR-1.2** 프론트·백엔드 프레임워크는 Construction NFR/기술스택 단계에서 고른다. 이번 문서는 모노레포 분리와 PostgreSQL만 고정한다.

### NFR-2 데이터

- **NFR-2.1** 정형 데이터(실적, 경영목표, 보고 요청, 문서 메타, 기사 확정 여부, 변경 History)는 PostgreSQL에 저장한다.
- **NFR-2.2** 업로드 원본 파일은 로컬 파일 저장소에 두고 DB에는 경로와 추출 텍스트를 둔다. 구체 방식은 Construction에서 정한다.

### NFR-3 Agent

- **NFR-3.1** Agent LLM은 OpenAI API를 사용한다.
- **NFR-3.2** 목표 확정 숫자는 모델이 만들지 않는다. 방향·범위만 제안한다.
- **NFR-3.3** Attention·해설·제안은 근거 ID 없이 완료된 것으로 보지 않는다.

### NFR-4 언어와 접근

- **NFR-4.1** 기본 locale 한국어. 영어 전환을 지원한다.
- **NFR-4.2** 사용자 대상 화면의 자동화용 식별자(`data-testid` 등)는 코드 생성 단계에서 안정적으로 붙인다.

### NFR-5 테스트 (PBT extension: 전면 적용)

- **NFR-5.1** 예제 기반 테스트에 더해, 비즈니스 로직·데이터 변환·직렬화에 property-based test를 적용한다.
- **NFR-5.2** Functional Design에서 컴포넌트별 testable properties를 식별한다 (PBT-01).
- **NFR-5.3** JSON 등 직렬화 round-trip, 경영목표 상태 전이 불변조건 등 해당 속성이 있는 곳에 PBT를 둔다.

### NFR-6 복원력 (Resiliency baseline: 적용, 로컬 Prototype)

이 워크로드는 **로컬 Prototype**이다. 프로덕션 다중 AZ/다중 리전 DR은 이번 범위에서 N/A이다. 아래는 Prototype에 적용하는 최소값이다.

- **NFR-6.1** 구성 요소 중요도: `apps/api`(High — Agent·저장), `apps/web`(Medium), PostgreSQL(High — 확정 목표·문서 메타). 데모 불가 영향은 내부 시연 중단이며 규제·매출 영향은 없다.
- **NFR-6.2** Prototype SLA: 로컬 프로세스가 떠 있는 동안 기능 제공. 가용성 % 목표는 두지 않는다.
- **NFR-6.3** RTO: 로컬 스택 재기동으로 복구. RPO: PostgreSQL 로컬 디스크. 데모 시나리오는 Mock seed로 재적재 가능해야 한다.
- **NFR-6.4** OpenAI·공식 도메인 검색 실패 시 Agent는 실패를 숨기지 않고, 내부 DB·이미 확정된 근거만으로 동작하거나 검색 불가를 표시한다.
- **NFR-6.5** 프로덕션 DR 전략·CI/CD·리전 토폴로지는 배포가 범위에 들어오는 단계에서 다시 묻는다.

### NFR-7 보안 (Security extension: 미적용)

- **NFR-7.1** Security baseline 규칙은 강제하지 않는다.
- **NFR-7.2** Mock 로그인은 데모용이다. 비밀은 환경 변수로 두고 저장소에 커밋하지 않는다 (OpenAI API 키).

## 5. Prototype이 증명해야 하는 End-to-End

1. Mock 로그인 (종합기획부)
2. 은행 Dashboard — 부문별 Attention 요약 목록, 보고 요청
3. 여신 Drill-down — 종합수익 / 기업여신 / 가계여신, 상세에서도 해당 Attention·근거
4. 경영목표 설정으로 이동 (필요 시 Attention을 검토 대상으로 등록)
5. 기존 목표 수정 필요 탐지
6. 당행 Data + 공식 정책 + 내부 의사결정(+ 확정 기사)으로 수정안 (방향+범위)
7. 신규 목표 제안 (포용금융). 근거: 가계여신 포용금융 지표 + 공식 정책 + 내부 의사결정 (데모 시드: 정부·외부 금융기관 포용금융 확대 관련 확정 언론보도, 행 내 포용금융 확대 논의 문서)
8. 반영 또는 직접 수정 후 확정
9. 확정 목표가 DB에 남아 이후 사업부서가 읽을 수 있는 구조
