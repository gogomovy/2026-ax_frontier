## 0. 한눈에 보기

```
업로드 ─┬─ 정형 자료(데이터셋 .csv/.xlsx/.json) ──▶ PostgreSQL {bank|ext}.row_store (JSONB 행)        ── 임베딩 X
        │                                          └─▶ 그래프: 데이터셋 정의의 '개념 매핑' · 계보만 (행 값은 그래프에 안 넣음)
        │
        ├─ 문서(.pdf/.hwpx/.hwp/.txt/.md/.html) ──▶ PostgreSQL {bank|ext}.document (전문) + .chunk (700자 청크)
        │                                          ├─▶ 벡터: chunk.embedding (pgvector — 임베딩 값 원장)  ← 워커 embed_chunks
        │                                          ├─▶ Elasticsearch 색인 nhdip-doc-chunk (현재 판 청크) ← 워커 1분 동기화
        │                                          └─▶ 온톨로지: document.extraction(JSONB) → Neo4j 투영 ← 워커 extract_documents · project_graph
        │
        └─ (사용자 업로드 요청) ── 승인 전까지는 위 어느 곳에도 들어가지 않음 → 승인 시 위와 같은 경로

게시된 분석 결과(화면 산출물) ──▶ PostgreSQL app.kb_chunk (분석 결과 청크 · 팀별 컬렉션 · 개념 태그)
                                  ├─▶ 벡터: kb_chunk.embedding (pgvector · 부분 HNSW)  ← 워커 60초 주기
                                  ├─▶ Elasticsearch 색인 nhdip-kb-chunk                ← 워커 1분 동기화
                                  │        키워드(BM25 + nori 형태소 + 사용자 사전) · 의미(kNN) 후보 찾기 전용 — 본문 · 벡터 원본은 PostgreSQL
                                  └─▶ 그래프: (Artifact)-[:MENTIONS]->(개념)          ← 투영

PostgreSQL 원장 ──collect_graph──┬─▶ Neo4j 투영 (그래프 탐색 · 근거 검색 개념 경로)
 (Neo4j 투영과 같은 수집 코드)    └─▶ 관리자 [온톨로지] '구성 지도' (3D 군집 · 2D · 구조도 · 표) — Neo4j 없어도 보임
```

- **3-way 구성(Phase H · Q130).** PostgreSQL = 원장(사실 · 문서 · 청크 · **임베딩 값** · 권한 · 감사)과 권한 판정, **Elasticsearch = 키워드 · 의미 검색**(분석 결과 · 문서 색인 두 개), Neo4j = 개념 그래프. ES · Neo4j 는 언제든 PostgreSQL 에서 다시 만들 수 있다.
- **벡터 값의 원장은 PostgreSQL `pgvector` 다**(`{bank|ext}.chunk.embedding`, `app.kb_chunk.embedding` — Q110 · Q131). ES 는 그 값을 복사해 kNN 으로 찾는다. 색인을 다시 만들어도 임베딩 모델을 다시 부르지 않는다.
- **Elasticsearch 가 표준 검색 엔진이다**(compose 기본 서비스, 검색 설정 `knowledge.search.backend` 기본 `auto`). AI 어시스턴트의 분석 결과 · 문서 키워드 · 의미 채널과 워크플로 근거 검색이 ES 에서 후보를 찾고, **ES 가 돌려준 후보는 PostgreSQL 에서 접근 규칙으로 한 번 더 걸러 읽는다**(권한 누수 0). ES 가 없거나 안 되면 같은 채널을 PostgreSQL(전문 검색 · pgvector)로 축소 동작한다 — §2.2.
- **Milvus 는 쓰지 않는다.** 벡터 전용이라 키워드(한국어 형태소) 검색을 따로 둬야 하고 구성 요소가 늘어난다 — §2.3.
- **원장은 PostgreSQL, Neo4j 는 투영본이다.** 그래프는 매번 PostgreSQL 에서 전체를 다시 만들 수 있다(`graph/projection.py`). 노드 · 관계 전용 PostgreSQL 테이블은 없다. 관리자 화면의 구성 지도도 Neo4j 가 아니라 이 원장 수집 결과로 그린다 — §4.7.
- **문서 → 온톨로지** 결과는 문서 행의 `extraction`(JSONB)에 저장되고, 검증을 통과한 것만 그래프가 된다.

| 무엇 | PostgreSQL (원장) | 벡터 값(pgvector) | Elasticsearch (검색 색인) | 온톨로지(Neo4j 투영 · 구성 지도) |
|---|---|---|---|---|
| 데이터셋 행 | `{origin}.row_store.data` | **안 함** | 안 함 | 행 값은 안 넣음. 데이터셋 정의 `mapping` 에 적힌 개념 · 상품 노드와 계보만 |
| 데이터셋 버전 | `{origin}.dataset_version` | 안 함 | 안 함 | `Dataset` · `DatasetVersion`(현재 버전) |
| 문서 전문 | `{origin}.document.text` | 안 함(청크만) | 안 함 | `Document` 노드(제목 · 분류 · 버전) |
| 문서 청크 | `{origin}.chunk.text` · `tsv` | **함** (`chunk.embedding`) | **복사**(현재 판만 · `nhdip-doc-chunk` · 권한 · 분류 필드) | 청크 단위 노드는 없음 |
| 문서 추출 결과 | `{origin}.document.extraction` | 안 함 | 안 함 | 개념 노드 + `MENTIONS` · `STATES_STANCE` · `SETS_CONSTRAINT` · `ISSUED_BY` |
| 추출 검토 대기 | `ops.extraction_issue` | 안 함 | 안 함 | 안 넣음 (`Candidate` 만 투영) |
| 분석 결과 청크 | `app.kb_chunk.text` · `tsv` · `concepts` | **함** (`kb_chunk.embedding`) | **복사**(`nhdip-kb-chunk` · 키워드 · 벡터 · 권한 필드, 본문은 `_source` 에서 뺌) | `Artifact -[:MENTIONS]-> 개념` |
| 지표 · 워크플로 정의 | `cfg.metric` · `cfg.workflow` · 트리거 | 안 함 | 안 함 | `Metric` · `Workflow` · `FEEDS` · `USES` · `PRODUCES` 등 계보 |

## 1. 업로드 경로별 흐름

### 1.1 정형 자료(데이터셋)

| 단계 | 내용 | 코드 |
|---|---|---|
| 입구 | 관리자 `POST /admin/datasets/{code}/upload` · 사용자 요청 `POST /db/uploads/dataset`(승인 후) | `api/admin_data.py` · `api/db_uploads.py` |
| 검사 | 보안(확장자 `.csv .tsv .xlsx .json`, 크기 `upload.policy.max_mb` 50MB) → 열 매핑 → 품질 검사(필수 열 · 규칙 · **개인정보 형식 값 검사** `privacy.policy.pii_scan`) | `data/filecheck.py` · `data/datasets.py` |
| 저장 | 원본 파일 `{FILESTORE_DIR}/{origin}/{code}/…`, 버전 `{origin}.dataset_version`(+1), 행 `{origin}.row_store.data`(JSONB · GIN 인덱스). 같은 기준월 구획의 이전 현재 버전은 내려감 | `ingest_rows` |
| 이벤트 | 확정되면 같은 트랜잭션에 `dataset.committed` (되돌리기도 `rollback: true` 로 같은 이벤트) | `events.emit` → `ops.outbox_event` |
| 이후 | 그 데이터셋을 쓰는 부서 워크플로(지표 계보 · 트리거) 재계산 + `wf_graph_projection`(그래프 재투영) | `workflow/dispatcher.py` |

- **데이터셋 행은 임베딩하지 않는다**(Elasticsearch 에도 올리지 않는다). 숫자는 계산 커널이 읽는 사실 값이라 검색 대상이 아니다.
- 그래프에는 데이터셋 정의(`cfg.dataset.mapping`)에 적힌 것만 들어간다 — §3.2 ①.

### 1.2 문서

| 단계 | 내용 | 코드 |
|---|---|---|
| 입구 | 관리자 `POST /admin/documents/upload`(출처 bank/ext · 분류 · 제목 · 발행처 · 시행일 · 파일 또는 본문 글) · 사용자 요청 `POST /db/uploads/document`(승인 후) · 시드 문서 | `api/admin_data.py` · `api/db_uploads.py` · `seed/run.py` |

| 분류 | `doc_class.labels`: 정부정책(gov_policy) · 경영 의사결정(mgmt_decision) · 모형 · 방법론(model_method) · 영업점 기준 · 공문(branch_ref) · 참고(reference). 기본 출처 `doc_class.default_origin`(정부정책 · 참고 = ext, 나머지 = bank) | `seed/defs_core.py` |

| 이벤트 | `document.ingested {origin, document_id, doc_code, doc_class}` | 같은 트랜잭션 |
| 이후 | `wf_graph_projection`: **① 임베딩(embed_chunks) → ② 온톨로지 추출(extract_documents) → ③ 그래프 투영(project_graph)** + 그 문서 분류를 읽는 부서 워크플로(근거 검색) | `seed/defs_data.py` · `workflow/nodes.py` |

- 보안 등급: 문서 `meta.accessClass = "dept_only"` 이면 설정 `docs.owner_orgs`(문서 코드 → 소유 부서)의 부서와 관리자만 본다. 현재 시드에서는 3건(`doc-mgmt-rwadept` 종합기획부, `doc-model-corp` · `doc-model-retail` 신용리스크관리부). **업로드 화면 · API 에는 이 등급을 지정하는 항목이 없어 업로드 문서는 항상 '행내'(internal)** 다.
- 문서 본문에는 적재 시 개인정보 검사 · 가림이 없다(데이터셋 행만 검사). 질문하기 색인(`app.kb_chunk`)은 가린다.
- **Elasticsearch 문서 색인**: 적재 트랜잭션에서는 ES 를 부르지 않는다. 워커가 1분마다 현재 판 청크를 대조해 올리고, 새 판이 적재되면 이전 판 청크를 지운다. 그 사이 새 판 청크는 검색이 PostgreSQL 로 보충한다(출처별 동기화 위치보다 큰 id).

### 1.3 사용자 업로드 요청(Phase C)

- [자료 올리기]에서 올리면 파일은 `{FILESTORE_DIR}/requests/…` 에 두고 `UploadRequest(pending)` 만 만든다. 데이터셋은 이때 품질 검사(실패면 요청 거절), 문서는 본문 추출 미리보기만.
- **승인 전에는 데이터 · 청크 · 벡터 · 검색 색인 · 그래프 어디에도 들어가지 않는다.**
- 관리자 또는 부서 데이터 책임자가 승인하면 파일 SHA 를 다시 확인하고 1.1 · 1.2 와 **같은 함수**(`ingest_file` · `ingest_document`)로 적재한다. 그때부터 이벤트 · 워크플로가 같다.

### 1.4 분석 결과(화면 산출물, Phase D)

- 워크플로가 화면 산출물(`app.view_artifact`)을 게시하는 **같은 트랜잭션**에서 질문하기 색인 `app.kb_chunk` 를 갱신한다(savepoint — 색인 실패해도 게시는 그대로). 워커가 60초마다 놓친 게시를 대조한다.
- 산출물을 결정적으로 문장화한다: 수치 마커 `[[fig:ID]]` → 커널이 확정한 값 · 단위 문장, 시계열 → '추이: …', 보고서 블록 · 표 → 행 문장. 개인정보 형식 값은 가린다.
- 청크 크기 900자 · 겹침 80자(`knowledge.index`), 본문 해시(`unit_hash`)로 같은 본문은 같은 행(임베딩 재사용).
- 청크마다 **컬렉션**(팀) · 열람 화면 리소스 · 지점 범위(`scope_key`) · 담당 조직 · **개념 태그**(`concepts` — 온톨로지 별칭 사전 부분 일치, 최대 40개)를 붙인다.
- 색인 제외: `documents` · `meta` · `change_feed` · `domains`.
- **Elasticsearch(표준)**: 게시 트랜잭션에서는 ES 를 부르지 않는다. 워커 주기 작업(`run_maintenance`, 1분)이 PostgreSQL 쪽 목록과 ES 목록을 대조해 바뀐 청크만 올리고 지워진 것은 지운다(§2.2). 아직 못 올린 새 청크는 검색이 PostgreSQL 로 보충하므로 게시 직후에도 잡힌다.

### 1.5 이벤트 → 워크플로 (공통)

| 이벤트 | 깨우는 것 |
|---|---|
| `dataset.committed` | 그 데이터셋을 쓰는 부서 워크플로 + `wf_graph_projection` |
| `document.ingested` | 그 문서 분류를 트리거로 둔 부서 워크플로(예: 정부정책 · 경영 의사결정 → `wf_inclusive_risk` · `wf_hq_goal_review`) + `wf_graph_projection` + 오케스트레이터(LLM) 추가 지정 |
| `ontology.changed`(관리자 스키마 저장) · `config.*` | `wf_graph_projection` |
| `kb.indexed`(분석 결과 색인 변경) | `wf_graph_projection` (Artifact → 개념 관계 반영) |

- `wf_graph_projection` 은 디바운스 5초로 이벤트를 합쳐 한 번 돈다. 근거 검색이 있는 부서 워크플로는 이 워크플로가 끝날 때까지 기다린다(`orchestrator.policy.evidence_upstream`).

## 2. 벡터 · 검색 색인에 저장되는 것

### 2.1 PostgreSQL pgvector (임베딩 값 원장 · ES 없을 때 의미 검색)

| 대상 | 테이블 · 열 | 단위 | 언제 | 모델이 바뀌면 | 인덱스 | 쓰는 곳 |
|---|---|---|---|---|---|---|
| **문서 청크** | `{bank,ext}.chunk.embedding` · `embedding_model` | 700자 청크 | `wf_graph_projection` 의 `embed_chunks` — 임베딩 없음 · **다른 모델**인 청크를 출처마다 실행당 최대 200건(현재 판 우선), 16건씩 | **다시 임베딩함**(Phase H — 분석 결과와 같은 규칙) | PostgreSQL 은 없음(순차 탐색) · **ES 문서 색인 kNN** | ES 문서 색인의 원본 · ES 가 없을 때 근거 검색 · AI 어시스턴트 문서 채널(같은 모델 벡터만) |
| **분석 결과 청크** | `app.kb_chunk.embedding` · `embedding_model` | 900자 청크 | 워커 60초 주기 `embed_pending` — 32건씩, 회당 160건, `FOR UPDATE SKIP LOCKED` | **다시 임베딩함**(`embedding_model != 현재 모델`) | **ES 분석 결과 색인 kNN** · PostgreSQL 은 모델 확정 후 `kb-hnsw --dim N`(부분 HNSW, 후보 풀 `hnsw_ef_search` 200 · 반복 탐색 `strict_order`) | ES 분석 결과 색인의 원본 · ES 가 없을 때 AI 어시스턴트 분석 결과 채널(`_kb_vector`) |

- 임베딩 모델: 설정 `embedding.agent` = `embedder` 에이전트(프로필 embedding) → 관리자 [LLM 연동]의 OpenAI 호환 `/embeddings`. 호출 기록은 `ops.llm_call`(purpose = embedding), 월 예산(`llm.budget`) 적용. ES 를 켜도 임베딩은 한 번만 계산해 PostgreSQL 에 저장하고, ES 에는 그 값을 복사한다.
- 열 차원을 고정하지 않았다 — 모델이 정해지지 않았기 때문. 검색은 질의 벡터와 차원이 같은 행만 비교한다.
- **HNSW 후보 풀 조정(접근 범위가 좁은 사용자)**: pgvector HNSW 는 가까운 후보를 먼저 찾은 **뒤에** 접근 범위(WHERE)로 거른다. 기본 후보 풀(40)이면 10만 건에서 영업점 사용자가 40건을 요청해도 평균 9.2건만 받았다. 후보 풀 200 + 반복 탐색으로 모든 범위에서 40/40건(설계 §21.18).
- **의미 거리 기준**: `max_cosine_distance`(기본 0.65)는 모델마다 눈금이 달라 지금 모델로 재서 정한다 — CLI `kb-calibrate [--apply]` · 관리자 [질문하기 색인] [보정 측정]. 두 분포(엉뚱한 질문 vs 제목 질문)가 갈릴 때만 적용할 수 있고 자동 적용은 하지 않는다(설계 §21.15).
- **임베딩 모델이 없으면** `embed_chunks` 는 '건너뜀' 으로 성공 처리되고 벡터는 NULL 로 남는다. 검색은 키워드(+개념 그래프)만으로 동작한다.

**임베딩하지 않는 것:** 데이터셋 행 · 문서 전문(`document.text`) · 추출 결과(`extraction`) · 그래프 노드 · 색인 제외 산출물 · 사용자 업로드 요청(승인 전).

### 2.2 Elasticsearch (3-way 표준 검색 엔진, `knowledge/elastic.py` · 설계 §24)

| 항목 | 내용 |
|---|---|
| 대상 | **분석 결과 청크(`app.kb_chunk`) · 문서 청크(`{bank,ext}.chunk`, 현재 판만)** — 색인 두 개. 그래프 채널 · 데이터셋은 PostgreSQL · Neo4j |
| 색인 | `nhdip-kb-chunk`(`ES_INDEX`, id = 청크 id) · `nhdip-doc-chunk`(`ES_DOC_INDEX`, id = `<출처>:<청크 id>`), 샤드 1 · 복제본 `es_replicas`(단일 노드 0), `dynamic: strict`, 정의 판 `_meta.nhdip`(판 · 사용자 사전 서명 — 다르면 동기화가 다시 만든다) |

| 동기화 | 워커 1분 주기(`sync_all`). PostgreSQL `(id, 권한 · 메타 · 본문 해시, 임베딩 모델)` 목록 ↔ ES 목록 대조 → 다른 것만 올리고 사라진 것(삭제 · 문서 이전 판)은 지움(멱등). 변경이 없으면 대조를 건너뛰고 15분마다 전체 대조, 회당 상한 `es_sync_max_per_run` 2,000. 검색 설정이 `pg` 여도 올려 둔다 |
| 검색 | 키워드: 어절마다 구문 일치 절 → 맞춘 절 수(`matched_queries`)가 점수의 정수부(PostgreSQL 채널과 같은 척도). 의미: kNN(`num_candidates` = 후보 수 × 10, 필터를 그래프 탐색 안에서 적용, 같은 모델 벡터만). 채널별 후보 `es_candidates` 60. **AI 어시스턴트(분석 결과 · 문서)와 워크플로 근거 검색(`hybrid_search` — 분류 · 개념 경로 문서 조건)이 함께 쓴다** |
| 권한 | ① 같은 접근 규칙을 ES 질의 필터로(분석 결과 `es_filter` ↔ SQL `kb_filter`, 문서 `doc_es_filter` ↔ SQL `doc_filter` — 범위별로 같은 청크 집합임을 실제 ES 시험으로 고정) ② **ES 가 돌려준 id 를 PostgreSQL 에서 다시 걸러** 본문을 읽는다 — 권한 필드가 낡았거나, 부서한정 · 볼 수 없는 분류 · 이전 판 · 지워진 청크여도 결과에 안 나온다 |
| 게시 · 적재 직후 | ES 에 아직 없는 청크(`id > synced_max_id`, 문서는 출처별)는 PostgreSQL 결과로 보충. 한 번도 동기화되지 않았으면 PostgreSQL 만 쓴다 |
| 장애 | 연결 오류 · 시간 초과 · 5xx → 차단기(30초 → 두 배씩 300초) · 그 채널만 PostgreSQL 로 자동 폴백(같은 답 모양). 응답 `retrieval.engines`(분석 결과 · 문서 · 그래프)가 실제로 쓴 엔진, 답 아래 검색 정보에 표시 |
| 구성 | **compose 기본 서비스** `elasticsearch`(nori 를 넣은 이미지 `infra/elasticsearch/Dockerfile`, ES 9.5.4) · `.env` `ES_URL=http://elasticsearch:9200` · `ES_USER=elastic` · `ES_PASSWORD`(make env 가 생성) · 호스트 `vm.max_map_count ≥ 262144`. 외부 ES 면 주소 · 계정만 바꾼다. 쓰지 않으려면 `ES_URL=` 로 비우고 검색 설정을 `pg` 로. **이전 `.env.example` 로 만든 `.env` 는 `ES_URL=` 이 비어 있을 수 있다** — `bash infra/scripts/set-env.sh ES_URL http://elasticsearch:9200` |
| 운영 도구 | CLI `python -m nhdip.cli kb-es [--sync\|--rebuild\|--check]`(인자 없으면 상태, `--check` 는 문제 있으면 종료 코드 1) · 관리자 [AI 어시스턴트 색인] **3-way 구성 카드**(PostgreSQL · Elasticsearch · Neo4j) · 운영 점검 `search_backend`(auto 인데 ES_URL 없음 · 연결 불가 · 동기화 미완 · nori 없음 경고) · CI e2e 가 ES 포함 스택에서 `kb-es --check` · 골든셋 |

### 2.3 왜 Milvus 가 아니고, 왜 pgvector 를 없애지 않나

| 선택지 | 판단 | 이유 |
|---|---|---|
| **Elasticsearch(또는 OpenSearch)** | **채택 — 3-way 표준 검색 엔진(Q130)** | 키워드(BM25 + nori 한국어 형태소) · 벡터(HNSW kNN) · 필터 · 결합을 한 엔진에서. 금융권 운영 사례가 많다. kNN 이 필터를 탐색 안에서 적용해 좁은 접근 범위에서도 재현율이 떨어지지 않는다 |
| Milvus | 쓰지 않음 | 벡터 전용 — 한국어 키워드 검색을 따로 둬야 하고(키워드 · 의미 · 그래프 세 채널 구조에 구성 요소가 늘어남) 기본 구성도 여러 서비스. 수억 건 벡터 전용 워크로드에 맞다 |
| pgvector 제거(ES 를 원장으로) | 하지 않음 | 접근 제어 기준(사용자 · 조직 · 컬렉션)이 PostgreSQL 에 있고, 색인 · 권한 변경이 게시 트랜잭션과 한 몸이다. 별도 엔진을 원장으로 두면 권한 필드 동기화 누락이 곧 권한 누수다. ES 는 언제든 PostgreSQL 에서 다시 만들 수 있는 **검색 색인**으로 둔다 |

처음 판은 '전환 신호가 오면 `backend = "es"`' 였다. Phase H 에서 사용자 지시로 **표준 구성(검색 설정 기본 `auto`)** 이 되었다 — PostgreSQL 키워드는 공백 낱말 + 접두 일치라 합성어 · 어간을 못 다루고(가장 큰 이유), 문서 원문 검색에서 그 차이가 크다. 운영(EC2 · 폐쇄망) 반영에는 ES 서버 메모리 · `vm.max_map_count` · 이미지(nori) 준비가 필요하다.

로컬 확인에서 하나 더: Elasticsearch 의 RRF 결합(`retriever.rrf`)은 기본(basic) 라이선스에서 403 이다. 이 시스템은 결합을 애플리케이션에서 하므로(점수 결합 · RRF 선택, §5) 영향이 없다(설계 §23.6).

## 3. 온톨로지에 저장되는 것 — 어떤 문서가 어떻게

### 3.1 문서 → 온톨로지 추출 (`graph/extraction.py`)

모든 **현재 버전 문서** 가 대상이다(분류 무관). `wf_graph_projection` 의 `extract_documents` 가 이번 이벤트의 문서와 `status = ingested` 인 문서를 처리한다.

| 모드 | 조건 | 방식 |
|---|---|---|
| **LLM 추출** | `ontology_extractor` 에이전트 연결됨 | 문서 **앞 12개 청크**까지 청크마다 호출. 입력 = 허용 클래스 · 관계 · 마스터 키 목록 + 분류 · 제목 · 청크 본문. 출력 JSON `{entities:[{label,key,name,props,evidence_span}], relations:[{type,from,to,props,evidence_span}]}` |
| **규칙 추출**(폴백) | LLM 미연결 또는 모든 청크 호출 실패 | 문서 **전문** 에서 별칭 사전 부분 일치 → 개념 + `MENTIONS`. 정부정책 · 경영 의사결정 문서는 그 개념이 나온 문장의 키워드로 `STATES_STANCE{direction}`(확대 · 활성화 · 강화 → expand / 관리 · 억제 · 건전성 · 안정화 → manage / 유지 → maintain) |

LLM 결과 검증(`validate`) — 통과한 것만 남는다:

1. 클래스 · 관계가 스키마에 있고 '추출 가능' 이어야 한다 → 아니면 `schema_violation`
2. **근거 문장(evidence_span)이 본문 또는 제목에 그대로 있어야** 한다(공백 · 따옴표 · 가운뎃점 차이 허용) → 아니면 `span_not_found`
3. 키를 **별칭 사전(마스터 키)으로 해석**: 정확 일치 → 공백 무시 일치 → 포함 일치(서로 다른 키를 가리키면 해석 안 함). 마스터 클래스(정책주제 · 상품군 · 세그먼트 · 신용평가모형 · 사업부문 · 자본제약)가 사전에 없으면 `unresolved_entity` 로 남기고 `Candidate` 노드(`<클래스>:<원문>`)로 둔다. 발행기관(Issuer)은 원문 그대로 키
4. 관계는 양끝 해석 · 방향(from → to 라벨) · 속성 허용값('확대' → expand 정규화)을 검사

저장: 문서 행 `extraction = {by: "llm:<모델>" | "rule", schema_version, entities, relations, issues}`, `status = extracted`(이슈 0) / `partial`(이슈 있음). 이슈는 `ops.extraction_issue` → 관리자 [온톨로지 › 추출 검토]. 근거 문장 · 면 번호는 구성 지도의 상세 패널에도 보인다(§4.7).

### 3.2 그래프 투영 (`graph/projection.py` — `collect_graph` → `project_all`)

수집(`collect_graph`)이 원장 전체를 모아 노드 · 관계 묶음을 만들고, 투영(`project_all`)이 그것을 라벨 · 관계 유형별로 Neo4j 에 `MERGE` 한 뒤 이번 세대(`proj_gen`)에 없는 관리 노드 · 관계는 지운다 → 멱등 · 자동 정리. 스키마에 없는 라벨 · 관계는 버리고 기록만 한다. **구성 지도(§4.7)는 같은 수집 결과를 쓴다**(Phase G 에서 수집 단계를 떼어 냄 — 투영 결과는 바뀌지 않음을 시험으로 고정).

| 순서 | 원천 | 만드는 것 |
|---|---|---|
| ① 데이터셋 | `cfg.dataset` + 현재 버전 + `mapping` | `Dataset` · `DatasetVersion` · `HAS_VERSION`. `mapping.nodes/edges` 가 있으면 **행 단위** 노드(현재는 상품 `Product` 와 `IN_GROUP` 만). `mapping.concepts` 는 고정 개념 노드와 그 사이 관계, `about: true` 면 `Dataset -[:DESCRIBES]-> 개념` |
| ② 계보 | `cfg.metric` · `cfg.workflow` · 트리거 | `Metric` · `FEEDS`(데이터셋 → 지표) · `DERIVED_FROM`(지표 → 지표) · `Workflow` · `USES` · `PRODUCES → Artifact` · `READS_CLASS → DocClass` |
| ③ 문서 | 현재 버전 문서 + `extraction` | `Document`(+ `BankDocument`/`ExternalDocument`) · `IN_CLASS → DocClass` · `ISSUED_BY → Issuer` · 추출 개념 노드 · `MENTIONS` · `STATES_STANCE` · `SETS_CONSTRAINT` |
| ④ 분석 결과 | `app.kb_chunk.concepts` | `Artifact -[:MENTIONS]-> 개념` (별칭 사전에 있는 개념만) |

Neo4j 가 없으면 투영 노드는 '축소 동작(degraded)' 으로 끝나고 다음 이벤트에서 다시 투영한다. 원장은 PostgreSQL 에 그대로 있고 구성 지도는 계속 보인다.

- 스키마를 저장하면 `ontology.changed` → 재투영. **이미 추출된 문서는 새 스키마로 다시 추출하지 않는다**(저장된 결과를 새 허용 목록으로 걸러 투영할 뿐). 다시 추출하려면 문서별 [재추출].
- 추출 검토에서 '확인' 해도 상태만 바뀐다(별칭 추가 · 그래프 반영은 별도).
- 되돌리기 전용 기능은 없다 — 이전 JSON 을 새 버전으로 다시 저장한다.

### 4.8 온톨로지 v3 · 구축 에이전트 (Phase M · 2026-10-15 · 설계 §30)

v2 까지는 시드가 정한 매핑(`dataset.mapping`)과 문서 추출만으로 그래프를 만들어, 팀이 새로 올린 자료는 객체 · 링크가 되지 못했다. v3 은 팔란티어식 객체 유형 · 링크 유형을 같은 판 JSON 에 둔다(별도 표 없음 — Q179).

| 항목 | v3 에서 더한 것 |
|---|---|
| 클래스 = 객체 유형 | `ko`(업무 이름) · `kind`(object · concept · document · system) · `primary_key` · `title_property` · `properties[{name, ko, base_type}]` · `backing[{dataset, key_col, title_col, props}]`(어느 데이터셋 행이 이 객체인지) · `implements[]` |
| 관계 = 링크 유형 | `ko` · `cardinality`(1:1 · N:1 · 1:N · N:M) · `inverse` · `backing[{dataset, from_col, to_col}]` |
| 인터페이스 | `cfg.ontology_schema.interfaces`(마이그레이션 0017) — 여러 객체 유형이 함께 가진 속성 묶음 |
| 투영 | `collect_graph` 가 `backing` 을 읽어 객체 · 링크를 만든다(관계 값은 별칭 해석기를 거침). 끝 노드가 없어 버려진 관계는 `Batch.dangling()` 으로 센다 |

구축 에이전트(`wf_ontology_build` — 데이터셋 반영 · 정의 변경 · 매일 07시):

| 단계 | 에이전트 | 하는 일(결정론 먼저, LLM 은 이름 · 의미 · 애매한 것만 — Q182) |
|---|---|---|
| 구조 파악 | `onto_profiler` | 열 통계 · 의미 유형(식별자 · 코드 · 이름 · 금액 · 비율 · 날짜 …) · 키 후보 → `ops.data_profile`(버전 묶음마다 한 번) |
| 객체 유형 설계 | `onto_modeler` | 원천 없는 데이터셋 → 기존 클래스의 원천(값 95% 이상이 그 클래스 키) 또는 새 객체 유형(측정값은 속성으로 복제하지 않음 · 이름은 표 종류 낱말 제거) |
| 링크 발견 | `onto_linker` | 차원 열 값이 다른 객체 유형 키에 들어가는 비율(포함률 0.95) → 링크 유형 · 다중도 |
| 개체 해소 | `onto_resolver` | 문서 추출의 미해석 후보 → 유사도 0.84 이상 별칭, 0.7~0.84 는 LLM 판정 |
| 품질 점검 | `onto_qa`(규칙) | 스키마 검증 · 범위 · 버려진 관계 · 키 중복 · 다중도 · 후보 적체 · 옛 판 추출 문서 → 등급(양호 · 주의 · 위험) |
| 변경 제안 | `onto_steward`(규칙) | 연산을 제안으로(대기 중 · 반영됨 · 반려된 연산 제외), `ontology.build.auto_apply` 에 둔 연산만 자동 적용(기본 없음) |

스키마는 관리자 [온톨로지 › 변경 제안]에서 연산별로 보고(예상 개체 · 관계 변화 · 검증 · 근거) 승인 · 반려 · 연산 빼기를 할 때만 바뀐다(Q181). 승인 = 새 판 + `ontology.changed` → 재투영 · 옛 판 추출 문서 재추출. [스키마 편집]의 판 이력에서 이전 판으로 되돌린다(새 판으로 — 이력 보존).

## 5. 저장한 것을 어디에 쓰나

| 쓰는 곳 | 벡터 · 키워드 | 온톨로지 |
|---|---|---|
| **워크플로 근거 검색** (`retrieve_evidence` → 서술 에이전트에 근거 문서 전달) | 문서 청크 키워드 · 의미 — **ES 문서 색인**(분류 · 개념 경로 문서 조건, PostgreSQL 재확인), ES 가 없으면 PostgreSQL → RRF 결합. 노드 결과 `searchEngine` | 워크플로별 개념(예: 포용금융 워크플로 = 포용금융 · 햇살론 · 새희망홀씨대출 · 사잇돌)을 `MENTIONS` · `STATES_STANCE` · `SETS_CONSTRAINT` 로 언급한 문서를 먼저 고름. 선별 우선순위 = 공식성 0.40 + 시점 0.25 + 의미 0.20 + **개념 경로 0.15** |

| **영향 범위** | — | `Dataset -FEEDS→ Metric ←USES- Workflow` 로 데이터 변경의 영향 워크플로 조회 |
| **구성 지도** (관리자) | — | 원장 수집 결과 전체(§4.7) |

Neo4j 가 없어도: 근거 검색은 개념 필터 없이 권한 범위 전체를 검색하고, 질문하기는 PostgreSQL 쪽 개념 채널(분석 결과 `concepts` · 데이터셋 매핑 간선)로 동작한다(질문하기는 연결 차단기로 실패 후 30초 → 최대 5분 동안 Neo4j 를 건너뜀). 구성 지도는 원장 기준이라 그대로 보인다. Elasticsearch 가 없어도(또는 장애) AI 어시스턴트 · 근거 검색은 PostgreSQL 로 같은 모양의 답을 낸다(운영 점검이 경고).

## 7. 직접 확인하는 방법

- 화면: 관리자 [온톨로지](구성 지도 · 그래프 관계 · 스키마 편집 · 추출 검토) · [질문하기 색인](컬렉션별 청크 · 임베딩 · 검색 엔진 상태 `searchBackend` · 거리 보정 · 품질 지표 · 사용자 관점 검색 진단) · [데이터셋 · 문서](문서 상태 · 재추출) · [운영 점검](`knowledge_index` · `search_backend` 항목)
- CLI: `python -m nhdip.cli kb-es`(두 색인 상태 — `ES_URL` 이 없으면 '설정되지 않음') · `kb-es --sync` · `kb-es --rebuild` · `kb-es --check`(3-way 점검) · `kb-calibrate` · `kb-hnsw --dim N`
- API: `GET /admin/ontology/map?limit=1500` (구성 지도 원자료 — `total` · `clusters` · `schema` · `classes`)
- SQL(읽기 전용 예):

```sql
-- 문서별 추출 결과
SELECT doc_code, doc_class, status, extraction->>'by' AS by,
       jsonb_array_length(extraction->'entities') AS entities, jsonb_array_length(extraction->'relations') AS relations
FROM bank.document WHERE is_current ORDER BY doc_class, doc_code;
-- 문서 청크 임베딩 현황
SELECT count(*) AS chunks, count(embedding) AS embedded, array_agg(DISTINCT embedding_model) FROM bank.chunk;
-- 질문하기 색인 컬렉션별 현황(ES 를 켜면 이 행들이 ES 로 복사된다)
SELECT collection_code, count(*) AS chunks, count(embedding) AS embedded FROM app.kb_chunk GROUP BY 1 ORDER BY 1;
-- 검토 대기 추출 이슈
SELECT kind, count(*) FROM ops.extraction_issue WHERE status = 'open' GROUP BY 1;
```
