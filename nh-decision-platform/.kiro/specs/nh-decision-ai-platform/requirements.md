## 1. 문서 목적과 범위

### 1.1 목적
본 문서는 은행의 경영 의사결정 프로세스(종합기획부 → 사업부서 → 영업점)를 Agentic AI로 지원하는 플랫폼의 **프로덕션 수준 기능/비기능 요구사항**을 정의한다. 단순 데이터 요약 도구가 아니라, 내부 정형 데이터·내부 비정형 경영정보·외부 정책 환경을 **온톨로지로 연결**하여 목표를 설정·조정·전파하는 의사결정 시스템을 대상으로 한다.

### 1.2 범위 (Scope)

| 구분 | 1차 구현 범위 (Production Slice) | 스켈레톤(껍데기)만 구현 | 비범위 |
|---|---|---|---|
| 조직 계층 | 종합기획부, 사업부서(**신용리스크관리부**), 영업점(목표 수신·수행 최소 기능) | 그 외 사업부서(여신관리부, 개인여신부 등), 지역본부 | 지주사 화면 |
| 사업 도메인 | **여신**(기업여신/가계여신/여신 종합수익/포용금융) | 수신, 퇴직연금, 자산관리, 신탁, 외환, 카드 | 그 외 |
| 의사결정 플로우 | ① 종합기획부 총자산·수익성 기반 경영목표 설정 ② 신용리스크관리부 모형 모니터링 ③ 포용금융 신용리스크 영향 모니터링 ④ 목표 전파(Cascade) | 사업부서별 추가 플로우 | 결재(전자결재) 연동 |
| 데이터 | 첨부 [데이터] 엑셀 6종 + [관련문서] PDF 7종, 온톨로지/그래프/벡터 적재 | 그 외 계정계·정보계 실시간 연계 | 전행 문서 자동 수집 |

### 1.3 용어 정의

| 용어 | 정의 |
|---|---|
| **[관련문서]** | 온톨로지에 적재되는 근거 문서(PDF/HWP 등). **원본 파일과 메타데이터를 항상 함께 보관**한다. |
| **[데이터]** | 정형 수치 데이터(엑셀). 사실(Fact) 테이블의 원천이 된다. |
| 종합기획부 | 은행 전체 총자산·수익·자본(RWA) 제약 하에서 사업부문별 경영목표를 설정하는 조직. |
| 사업부서 | 경영목표를 수행 방안(실행 계획·관리 기준·가이드)으로 번역하는 본부 부서. 1차 대상은 신용리스크관리부. |
| 영업점 | 사업부서가 내린 가이드라인·목표를 실제로 수행하는 현장 조직. |
| 경영목표(Management Goal) | 종합기획부가 확정한 사업부문별 목표. 하위 조직 Agent의 공통 판단 기준이 된다. |
| Attention | Agent가 사용자 질문 없이 선제적으로 탐지해 제시하는 확인 필요 사항. |
| Insight / 의견(Opinion) | Agent 분석 결과로 생성된 판단 문장. 항상 근거(Evidence)와 계산 추적(Calc Trace)을 가진다. |
| Evidence | 판단의 근거. `당행 Data` / `내부 경영방향` / `외부 정책·환경` 3범주로 구분한다. |
| 계산 커널(Calc Kernel) | LLM이 아닌 결정론적 코드로 수치를 계산하는 엔진. |
| PSI | Population Stability Index. 모형 입력/등급 분포 안정성 지표. |
| AR | Accuracy Ratio(= Gini). 부도예측 변별력 지표. |
| SDR | Standardized Default Rate(서열화 확인용). |
| RWA | Risk-Weighted Assets(위험가중자산). |
| 포용금융 대상 | "포용금융 대상 상품 대상자". 상품코드 기준으로 식별한다(§9.3). |

### 1.4 요구사항 표기 규칙
- ID 체계: `영역-번호` (예: `GOAL-06`). ID는 설계서·태스크 문서에서 그대로 추적된다.
- 수락 기준은 EARS 형식을 따른다: `WHEN <조건> THEN 시스템은 <동작>해야 한다(SHALL)`.
- 우선순위: **M**(MUST, 1차 릴리스 필수) / **S**(SHOULD, 가능하면) / **L**(LATER, 차기).

## 2. 제품 비전과 핵심 원칙

### 2.1 비전
> "은행 실적을 설명하는 AI"가 아니라, **내·외부 정보를 연결하여 경영목표의 설정과 조정을 지원하고, 그 결과를 조직 전체의 판단 기준으로 전파하는 AI**.

### 2.2 Product Loop
```
MONITOR ──▶ INTERPRET ──▶ SET DIRECTION ──▶ PROPAGATE ──▶ (EXECUTE/FEEDBACK) ──┐
   ▲                                                                            │
   └────────────────────────────────────────────────────────────────────────────┘
```
| 단계 | 종합기획부 | 사업부서(신용리스크관리부) | 영업점 |
|---|---|---|---|
| MONITOR | 은행 전체 사업부문 현황·Attention | 모형 적정성·포용금융 리스크 | 목표 대비 실적 |
| INTERPRET | 총자산 제약 + 수익성 + 정책 | 통계 검증 + 정책 정합성 | 가이드 해석 |
| SET DIRECTION | 경영목표 수정/신설 | 중점관리사항·가이드·수행방안 | 실행 계획 |
| PROPAGATE | 사업부서로 전파 | 영업점 가이드라인·목표 배분 | 실적 보고/확인요청 상향 |

### 2.3 공통 원칙 (전 화면·전 Agent 공통 적용)

| ID | 원칙 | 요구 내용 | 우선순위 |
|---|---|---|---|
| PRIN-01 | **Dashboard First** | 빈 Chat에서 시작하지 않는다. 화면 진입 시 이미 Agent가 분석을 마친 현황과 Attention이 제시되어야 한다. 추가 질문은 그 결과 위에서 이루어진다. | M |
| PRIN-02 | **Proactive Agent** | 사용자 질문 전에 목표 이탈 영역, 실적 변화, 목표 재검토 필요사항, 외부 정책 변화, 내부 의사결정사항, 타 조직 확인·보고 요청을 선제 탐지한다. | M |
| PRIN-03 | **Evidence First** | 모든 제안은 근거와 함께 제시한다. 근거 없는 수치·지시 문장 출력을 금지한다. 근거는 `당행 Data`/`내부 경영방향`/`외부 정책·환경` 3범주로 구분 표시한다. | M |
| PRIN-04 | **Traceability** | `Agent 판단 → 판단 근거 → 근거 데이터/문서 → 원문(페이지/셀)` 경로를 UI에서 끝까지 추적할 수 있어야 한다. | M |
| PRIN-05 | **Deterministic Numbers** | 화면·보고서에 표시되는 모든 수치는 계산 커널의 계산 결과(`calc_run`) 또는 원천 데이터(`metric_value`)에서만 유래해야 한다. LLM이 생성한 수치는 렌더링 단계에서 차단된다(§7). | M |
| PRIN-06 | **No Unsupported Causality** | 상관관계·기여도를 원인으로 단정하지 않는다. 허용 표현: "주요 영향 요인", "주요 기여 영역", "원인 후보", "현재 데이터상 확인되는 주요 변화". | M |
| PRIN-07 | **Alignment Check(배치 검증)** | 사업부서 Agent가 가이드·제안을 생성할 때 정부정책 DB, 경영 의사결정 DB, 종합기획부 경영계획과 **배치되는 내용이 없어야 하며**, 반영한 항목은 근거로 함께 표시해야 한다. | M |
| PRIN-08 | **Human-in-the-Loop** | 목표 확정, 가이드 확정, 목표 전파는 항상 사람의 명시적 승인으로만 수행된다. Agent는 제안까지만 한다. | M |
| PRIN-09 | **Reproducibility** | 동일 기준일·동일 데이터 스냅샷에 대해 수치 분석 결과는 항상 동일해야 한다(서술문은 버전 기록). | M |
| PRIN-10 | **Source Separation** | 내부 DB 근거와 외부 최신 수집 자료를 사용자가 구분 인지할 수 있도록 표시한다. | M |

## 3. 페르소나 및 권한

### 3.1 페르소나

| 코드 | 페르소나 | 핵심 질문 | 1차 구현 |
|---|---|---|---|
| P1 | 종합기획부 담당자 | "경영진이 어디에 Attention을 두어야 하며, 어떤 경영목표를 설정·수정해야 하는가?" | 전체 |
| P2 | 신용리스크관리부 담당자 | "모형과 포용금융 추진이 신용리스크 관점에서 적정한가? 무엇을 중점 관리해야 하는가?" | 전체 |
| P3 | 영업점 담당자 | "내게 내려온 목표와 가이드는 무엇이고, 지금 어떻게 수행해야 하는가?" | 스켈레톤 |
| P4 | 시스템 관리자 | 문서·데이터·온톨로지·Agent 운영 | 최소 |

### 3.2 권한 요구사항

| ID | 요구사항 | 수락 기준 | 우선순위 |
|---|---|---|---|
| AUTH-01 | **플랫폼 진입 = 로그인.** 미인증 사용자는 로그인 화면으로 이동하고, 로그인 후 사용자의 소속 조직과 역할로 진입 화면·메뉴가 결정된다. 사내 SSO 는 차기에 Provider 교체로 연동한다(AUTH-05). | WHEN 미인증 상태로 업무 화면에 접근하면 THEN 로그인 화면으로 이동하고, 로그인 후 원래 요청 경로로 복귀해야 한다. 페르소나 스위처는 개발 플래그가 켜진 환경에서만 노출된다. | M |
| AUTH-02 | 페르소나별 데이터·화면 접근 범위를 분리한다. | WHEN P2 사용자가 종합기획부 전용 목표 확정 API를 호출하면 THEN 시스템은 403을 반환해야 한다. | M |
| AUTH-03 | 문서에 접근등급(공개/행내/부서한정)을 부여하고, 검색·근거 표시 단계에서 등급을 필터링한다. | WHEN 부서한정 문서가 타 부서 사용자 질의의 근거 후보로 검색되면 THEN 해당 문서는 결과에서 제외되고 근거 목록에도 노출되지 않아야 한다. | M |
| AUTH-04 | 모든 조회·제안·확정 행위는 감사 로그에 기록된다(사용자, 시각, 대상, 근거 ID, Agent Run ID). | WHEN 경영목표가 확정되면 THEN 시스템은 변경 전/후 값과 근거 ID 목록을 포함한 불변 감사 레코드를 생성해야 한다. | M |
| AUTH-05 | 인증은 교체 가능한 Provider 구조(`local` = 사번·비밀번호 / 차기 `sso`)로 구현한다. | WHEN Provider 설정이 바뀌면 THEN 화면·권한 로직 수정 없이 인증 수단만 교체되어야 한다. | M |
| AUTH-06 | **사번 기반 회원가입**: 8자리 숫자 사번 · 성명 · 비밀번호 · 소속(본부 > 부 > 국 > 팀 또는 지역본부 > 영업점)으로 가입한다. 가입 직후 상태는 `승인 대기`이며 관리자가 승인해야 로그인할 수 있다. | WHEN 사번이 8자리 숫자가 아니거나 이미 가입된 사번이면 THEN 가입이 거부되고 사유가 표시되어야 한다. WHEN 승인 전 로그인하면 THEN `관리자 승인 대기` 안내가 표시되어야 한다. | M |
| AUTH-07 | **조직 계층**: 조직은 하나의 트리로 관리한다 — 본점 `본부 > 부 > 국 > 팀`, 영업 조직 `지역본부 > 영업점`(지역본부 직속 국·팀 허용). 조직 유형과 허용 상위 유형은 설정으로 관리하며(관리자 화면), 가입 시 소속은 이 트리에서만 선택한다(자유 입력 금지). | WHEN 조직이 비활성화되면 THEN 신규 가입 선택지에서 제외되고 기존 소속 사용자는 관리자 재배정 대상으로 표시되어야 한다. | M |
| AUTH-08 | **조직 기반 화면 권한**: 화면(메뉴) 접근은 `조직 → 화면` 권한 정의로 결정되며, 상위 조직에 부여한 권한은 하위 조직(부·국·팀 / 영업점)에 상속된다. 역할(`admin` / `user`)은 관리자 화면 접근만 추가로 제어한다. | WHEN 사용자에게 권한이 없는 화면 URL 을 직접 입력하면 THEN 403 화면이 표시되고, 해당 화면의 API 도 403 을 반환해야 한다(프론트 우회 방지). | M |
| AUTH-09 | **세션·보안**: 비밀번호는 단방향 해시(Argon2/bcrypt), 세션은 HttpOnly·SameSite 쿠키의 서명 토큰으로 관리하고, 연속 로그인 실패 시 잠금한다. | WHEN 로그인 5회 연속 실패하면 THEN 계정이 잠기고 관리자 해제 전까지 로그인할 수 없어야 한다. 비밀번호 원문·토큰은 로그에 남지 않아야 한다. | M |
| AUTH-10 | **최초 관리자**: 배포 시 환경변수로 지정한 사번이 최초 관리자로 생성되며, 이후 관리자 지정·해제는 관리자 화면에서만 가능하다. | WHEN 관리자가 1명뿐이면 THEN 그 관리자의 권한 해제는 거부되어야 한다. | M |
